Status: Draft  
创建日期：2026-09-18  
依据：[项目并行开发改造方案](PARALLEL_DEVELOPMENT_PLAN.md)

## 1. 实施目标与范围

在同一个 Git 项目中，使开发 A、开发 B 能够使用独立需求文档、独立 worktree、独立运行状态同时推进，并能各自暂停、恢复、验证和提交。

本实施保留源方案的边界：

- 一个需求对应一个活动 worktree；一个 worktree 同时只有一个写入编排器。
- 文档放在 `docs/harnessflow/<feature_id>/`，源码路径仍相对工作树根目录。
- 独立需求之间通过 worktree 隔离；需求内部继续使用现有批次并行机制。
- worktree 由用户创建，首版不增加自动创建、删除或跨需求调度能力。
- 最终合并由人工主导。用户决定合并时机、目标分支、顺序和业务冲突取舍；可以指示 AI 执行 Git 操作和合并后验证，不增加自动合并器。
- 保留需求、设计和实施书的批准规则，以及独立验证、人工交接和失败重试规则。

本轮交付仅为这份实施文档，不更新正在使用的 `docs/harnessflow/03_TASKS.json` 或 `04_STATE.md`。未来如需通过 `/hf-run` 执行本改造，需先在独立改造流程中补齐对应需求、设计和任务图，并将本文的任务、路径和验收条件一一映射；不要把本文直接当成已有任务图。

## 2. 开工准备与统一约定

### 2.1 开工检查

1. 记录当前 Git 根目录、分支、HEAD、暂存和未提交文件清单。若 HarnessFlow-CC 位于更大 Git 仓库内，变更范围仍限定在本项目目录。
2. 在独立开发分支实施。已有未提交改动不得自动清理、暂存或混入本次提交。
3. 记录 Python、Git、Node.js、Bash 和 Claude Code 版本。Python 继续使用项目现有的 3.10+ 标准库方案，不为锁或路径解析新增第三方依赖。
4. 运行 Python 或测试之前，先执行下列命令，核对其输出与用户激活的 Conda 环境；不一致时停止 Python 操作并报告。

   ```text
   python -c "import sys; print(sys.executable)"
   ```

5. 环境匹配后，从项目根目录运行现有回归基线，记录结果。已有失败与本次新增失败分别追踪。

   ```text
   python -m unittest discover -s tests -p "test_scope_guard.py" -v
   ```

6. 后续测试在临时仓库进行。真实用户项目、其 worktree、运行锁及 scope 不作为破坏性测试对象。

### 2.2 路径与上下文契约

以下契约在 P01 冻结，后续任务读取同一份解析结果：

| 字段或位置 | 约定 |
| --- | --- |
| `feature_id` | 稳定的小写英文、数字、连字符标识；具体长度和保留名检查在 P01-T02 落实 |
| `worktree_root` | 由 `git rev-parse --show-toplevel` 得到，不能直接假定等于启动目录 |
| `git_dir` | 由 `git rev-parse --absolute-git-dir` 得到，是本 worktree 的私有 Git 目录 |
| `common_dir` | 由 `git rev-parse --path-format=absolute --git-common-dir` 得到，仅用于跨 worktree 的需求锁 |
| `docs_root` | `<worktree_root>/docs/harnessflow/<feature_id>` |
| `runtime_root` | `<git_dir>/harnessflow/features/<feature_id>` |
| 工作目录绑定 | `<git_dir>/harnessflow/context.json`，不保存任务进度 |
| 工作目录锁 | `<git_dir>/harnessflow/writer.lock/` |
| 需求锁 | `<common_dir>/harnessflow/feature-locks/<feature_id>.lock/` |
| 公共资源 | 清单继续位于 `docs/harnessflow/`，模板位于 `templates/`，不因选择需求而改成需求私有路径 |
| 身份与基线 | 主会话身份、子代理归属、`run_id`、当前命令模式、当前分支及基线提交；身份来源必须通过 P01-T01 的实测 |

普通仓库的 `git_dir` 可能与 `common_dir` 相同；linked worktree 的私有运行目录必须与其他工作目录不同。不能为了兼容 `.git` 文件而将所有运行状态改放到共享目录。

`feature_id` 出现在任务图顶层、文档 `Feature:` 字段和代理摘要中。已有阶段、任务和需求编号只在本需求内检查唯一性。所有路径先正规化并核对所属目录，再读写。

### 2.3 锁与受控操作契约

统一顺序为：解析候选上下文 → 原子获取工作目录锁 → 原子获取需求锁 → 建立或核验绑定 → 执行写入 → 等待子代理停止 → 记录结果 → 清理本次 scope → 释放本次锁。

约束：

- 第二把锁获取失败，只释放本次刚获得的第一把锁；不删除已存在锁。
- 锁目录已创建但元信息尚未完整写入时，也视为占用或待恢复，不视为空闲。
- 锁和 scope 记录本次所有者及 `run_id`；延迟返回的旧代理不能清理新运行实例的文件。
- 文件写入使用临时文件加原子替换，不能让读取方看到半份 JSON；替换不能代替所有权校验。
- 正常暂停和等待人工处理时，在所有子代理停止后释放写锁，保留进度及需求绑定。
- 残留锁由显式恢复流程处理；PID、时间戳和模型自报身份不能单独作为抢占依据。
- `hf-status` 不创建绑定、不写默认配置、不修复状态、不获取写锁。

解析、锁、绑定和运行文件操作集中在一个小型共享模块 `.claude/hooks/hf_context.py`，同时提供受控命令行入口。模块不提供可写任意路径的通用接口。真实会话身份的取得和传播方式以 P01 的实验结果为准，不预先假定某个 hook 字段一定存在。

### 2.4 任务执行与证据

- 本文有 P01 至 P05 五个阶段、17 个任务；所有任务初始为 `todo`。
- 每个任务只修改其列出的文件。测试发现范围外问题时，交回相关任务修复，不扩大 worker 范围。
- 每个阶段交付一份 `docs/parallel-development-evidence/P0N.md`，记录任务结果、命令、退出码、必要日志路径、未解决问题及实际验证环境。
- 真实 Claude Code 行为记录在 `docs/parallel-development-evidence/HOOK_COMPATIBILITY.md`。只保存验证所需的脱敏事件和结论，不提交完整用户会话日志。
- 阶段通过后再进入下一阶段；证据文件由阶段收口统一写入，不由并行 worker 同时追加。
- 文档和配置均使用 UTF-8 无 BOM，保留已有中文和非 ASCII 文本。

## Phase P01: 上下文与所有权基础

依赖：无。交付：`docs/parallel-development-evidence/P01.md`。

Definition of Done：真实会话和子代理身份链有证据；路径、选择规则和锁接口已冻结；失败不会写入猜测位置或抢占其他所有者。

### Task P01-T01: 验证宿主 hook 与子代理身份

- 依赖：无；执行方式：只读调研及独立临时项目实验。
- 允许路径：`docs/parallel-development-evidence/HOOK_COMPATIBILITY.md`、`tests/fixtures/hook-events/`；探针只安装在临时项目，不改产品 hook 注册。
- 实施步骤：记录宿主版本；观察主会话、派生 worker、worker 失败、顶层会话停止和恢复时的实际事件；确认身份关联信息的来源、生命周期以及通过受控入口核验的方法。
- 产出：必要的脱敏事件样例，以及“事件 → 会话所有者 → 子代理 → 运行实例”的验证说明；明确缺失事件或异常事件的处理方式。
- 验证：启动两个顶层会话和至少一个子代理，证明合法子代理可关联到主会话，另一个顶层会话不能仅凭同一工作目录被当成合法所有者。
- 验收：身份来源、传播和终止均有实测依据；不能只提交一份自造 JSON 或环境变量假设作为通过证据。
- 阻塞处理：宿主不具备必要能力或当前无法完成实测时，记录具体缺口；可以继续独立路径研究，但 P01 不得标为通过，P02/P03 的执行授权接入不能跳过此门槛。

### Task P01-T02: 实现上下文解析和需求选择

- 依赖：P01-T01；允许路径：`.claude/hooks/hf_context.py`、`tests/hf_test_support.py`、`tests/test_hf_context.py`。
- 实施步骤：通过 Git 查询根目录、私有目录和共享目录；定义只读解析输出；校验 `feature_id`；区分纯旧版、新式目录和混合目录；实现显式参数、本地绑定及旧版兼容的选择规则。
- 固定规则：标识长度为 1 至 64 个字符，首尾为小写字母或数字，中间可含连字符；拒绝 Windows 保留名称、路径穿越及与公共目录冲突的名称。为 legacy 内部标识保留名称，不能让用户创建同名需求。
- 旧版映射：文档根仍为 `docs/harnessflow/`，运行文件迁入私有 runtime 中的 legacy 子目录，仍经过新版锁和授权逻辑；不继续从旧 scope 直接恢复执行。
- 测试内容：临时普通仓库、两个真实 worktree、子目录启动、中文和空格路径、缺参数、绑定冲突、Git 失败、损坏绑定、混合结构、非法标识及链接外逃。
- 验证命令：`python -m unittest discover -s tests -p "test_hf_context.py" -v`。
- 验收：解析不创建文件；两个 worktree 的 runtime 不同；Git 解析失败不回退 CWD；没有绑定时不猜需求；源码 `allowed_paths` 的基准保持为工作树根目录。

### Task P01-T03: 实现原子互斥与受控绑定

- 依赖：P01-T02；允许路径：`.claude/hooks/hf_context.py`、`tests/test_hf_locks.py`。
- 实施步骤：实现原子获取两把锁、所有权核验、绑定、释放和显式恢复入口；将 P01-T01 验证的身份关系接入；新增仅由所有者调用的运行状态操作基础。
- 分支与上下文：取得写入权后核对实际工作目录及分支；运行期间分支变化或绑定变化必须阻断，不自动重绑定。正常解绑要求无活动 worker，并且没有未处理的本流程改动。
- 测试内容：使用独立进程同时竞争；覆盖第二把锁失败、创建中断、重复释放、错误所有者、旧 `run_id` 清理新实例、残留锁和子代理合法继承。
- 验证命令：`python -m unittest discover -s tests -p "test_hf_locks.py" -v`。
- 验收：每次竞争只有一个成功者；失败方不改变绑定或 scope；正常子代理不被当成第二个顶层会话；无法确认旧写入者已停止时不接管。

## Phase P02: 文档、命令与代理上下文隔离

依赖：P01 通过。交付：`docs/parallel-development-evidence/P02.md`。

Definition of Done：A、B 可以使用同样的阶段和任务编号生成独立需求文档；公共资源和源码路径仍解析正确；所有代理收到明确的需求上下文。

### Task P02-T01: 更新共享契约和完整模板

- 依赖：P01；允许路径：`.claude/skills/harnessflow/SKILL.md`、`.claude/skills/harnessflow/MODELS.md`、`templates/`。
- 实施步骤：写入统一标识、选择、路径、锁和恢复规则；从现有文档提取缺失模板，补全 `00` 至 `04`、交付和交接模板；任务图模板增加 `feature_id`，文档模板增加 `Feature:`。

- 验证：在两个临时需求目录渲染模板，检查标识与目录一致、JSON 可解析、阶段与任务 ID 对应、模板引用存在、文件编码正确；记录模型配置从私有 runtime 读取的示例。

### Task P02-T02: 接入四个命令的参数和文档路径

- 依赖：P02-T01；与 P02-T03 并行。
- 允许路径：`.claude/commands/hf-design.md`、`hf-plan.md`、`hf-run.md`、`hf-status.md`（均位于 `.claude/commands/`）。
- 实施步骤：解析完整参数串；接入 `--feature`；支持已有 `P03`、`P03+`，以及 hf-plan 的指定阶段语义；所有写命令调用受控绑定和锁入口；修改 `argument-hint`、必要工具权限、输入及输出路径。
- 状态查询：只读解析指定需求；显示 feature、工作目录、分支、锁所有者和进度。跨文件读取遇到正在更新导致的短暂不一致，应报告读取时状态，不自行修复或误判为已完成。

- 验收：不再依赖 `$1` 判断所有参数；第二个写入会话在创建文档前被拒绝；设计和规划不会读取其他需求的状态；本任务只完成 hf-run 入口接入，批次运行细节在 P03 落实。

### Task P02-T03: 参数化校验脚本和报告路径

- 依赖：P02-T01；与 P02-T02 并行。
- 允许路径：`scripts/validate-ears.sh`、`scripts/test-coverage-report.js`、`scripts/run-sensors.py`、`tests/test_hf_reports.py`。
- 实施步骤：EARS 校验继续接受明确的需求书文件；coverage 脚本增加 `--docs-root`；sensor 脚本保留 `task_id` 和 `--project-root`，增加 `--docs-root` 并写入其 `reports/`。选中的目录来自统一解析入口，不在脚本中再次猜测当前需求。
- 兼容策略：默认旧路径仅用于确定的纯旧版调用；新式入口始终传参。混合结构、缺失显式目标、目标越界或输入不存在时给出非零退出码；不默默退回根目录。
- 测试内容：两个需求重复使用同一任务 ID 时报告不覆盖；检查读取的需求编号及任务归属；验证公共清单仍从公共位置读；不改变传感器算法或覆盖率口径。
- 验证命令：`python -m unittest discover -s tests -p "test_hf_reports.py" -v`；测试驱动现有 Node.js、Bash 和 Python 脚本，缺少运行时要明确记录，不能计为通过。
- 验收：A 的检查只使用 A 的输入并输出到 A；改变 `--docs-root` 不改变被扫描的源码根目录；新路径不存在时不会生成另一套隐式流程。

### Task P02-T04: 贯通所有子代理的任务包与返回值

- 依赖：P02-T02、P02-T03；允许路径：`.claude/agents/hf-phase-orchestrator.md`、`hf-phase-lead.md`、`hf-task-worker.md`、`hf-test-worker.md`、`hf-verifier.md`、`hf-explorer.md`（均位于 `.claude/agents/`），以及 `.claude/commands/hf-run.md`。
- 实施步骤：任务包携带需求、目录、运行标识和验证基线；代理从显式路径读设计、任务图、交接和报告；摘要返回 `feature_id`；主会话拒收不匹配的摘要。
- 边界：explorer 和 verifier 不取得写入权；worker 不切换需求、不改任务图和账本；编排层的合法产物写入通过明确角色及受控入口授权，不能给所有 worker 放行整个 `docs/`。
- 验证：人工复核六个代理定义及派发模板；用 A、B 同编号任务包做最小派发，检查实际读写路径和返回归属，证据写入本阶段报告。
- 验收：所有层级均无需从聊天记录推测需求；预算、模型和报告路径能追溯到同一上下文；本阶段的中间产物只在测试环境使用，不作为可发布的并行版本。

## Phase P03: 执行、守卫与恢复隔离

依赖：P02 通过。交付：`docs/parallel-development-evidence/P03.md`。

Definition of Done：真实双 worktree 可以独立写入、验证和暂停；一个流程的清理不能改变另一个的 scope、锁或账本；受控更新不依赖对 Git 内部目录的宽泛放行。

### Task P03-T01: 改造 scope guard 和受控状态更新

- 依赖：P02；允许路径：`.claude/hooks/hf_context.py`、`.claude/hooks/hf_scope_guard.py`、`.claude/hooks/hf_guard.sh`、`.claude/settings.json`、`tests/test_scope_guard.py`。
- 实施步骤：hook 使用统一解析及身份校验；保护旧版及所有新式目录中的任务图和状态；禁止当前流程写其他需求文档；取消 `GIT_CARVE_OUT` 的宽泛放行；按 P01 实测结果仅注册必要的宿主事件。
- 受控更新：明确只有主会话能更新任务图和账本；阶段编排器只能维护本次批次 scope 及被授权产物；worker 不能借辅助入口修改编排状态。辅助入口只接收既定操作及数据，不接受任意目标路径或 shell 片段。
- 模式区分：design/plan 没有批次 scope 是正常状态；run 的活动批次缺失、损坏或拥有错误 feature/run 标识则阻断。异常 hook 输入在活动受控流程中不能无条件放行；无关工具事件仍按匹配规则处理。
- 测试调整：保留 glob、越界及危险 Git 命令回归。现有“无 scope 放行任意写入”和“直接写 scope 被放行”的用例须改为按模式、身份判定，不能为了保留旧断言而恢复宽泛权限。
- 验证命令：`python -m unittest discover -s tests -p "test_scope_guard.py" -v`，并用 P01 真实事件样例验证各工具分支。
- 验收：合法控制操作能写到 worktree 私有运行目录，普通写工具无法借此写其他 Git 文件或仓库外路径；错误身份和过期运行标识被拒绝；文档继续明确 Bash 检查不等于操作系统沙箱。

### Task P03-T02: 接入批次运行与退出生命周期

- 依赖：P03-T01；与 P03-T03 并行。
- 允许路径：`.claude/commands/hf-run.md`、`.claude/agents/hf-phase-orchestrator.md`。
- 实施步骤：按私有 runtime 初始化或读取配置；每批写入带 feature/run 标识的 scope 后才派 worker；验证通过后只清理本次 scope；阶段间继续复核当前绑定、分支和基线。
- 暂停与失败：等待 worker 退出，保存准确的 `blocked`、`awaiting_human` 或已验证结果，再释放锁；未收到退出证据时不得解锁启动第二个写入会话。
- 恢复：重新读取文档、Git 状态和验证证据，核对残留锁及原会话状态；不能把旧的 `running` 自动改成 `done`，也不能沿用过期 scope。
- 提交：保持现有实现提交和状态提交的两步约定，提交消息带需求与阶段；将 P03-T03 的已核验文件清单作为暂存输入，不调用无范围的 `git add .` 或 `git add -A`。

- 验收：延迟返回的 A 子代理不能清理 A 的新运行实例或 B；所有停止路径都报告可执行的恢复条件；没有自动 push 或自动 merge。

## 6. 最终合并操作清单

这一节描述改造后的 A/B 开发成果如何进入目标分支；它不是自动执行的工作流。

1. **交付分支结果。** A、B 分别提供分支名、已验证提交、需求目录、测试结果和已知限制；确认没有未记录的活动 worker 或未处理的运行状态。
2. **人工决定集成方式。** 用户指定目标分支、合并时机和顺序；有前置依赖的需求先合入。用户可以指示 AI 执行后续 Git 命令与验证。
3. **检查目标基线。** 确认实际目标提交和工作区状态，避免在无关未提交改动上合并；不自动 stash、清理或修改已有历史。
4. **逐个合并。** 无冲突时继续验证；有冲突时记录涉及模块及原因。明确的机械冲突可以由 AI 处理，涉及行为选择或需求取舍时由用户决定。
5. **保留独立文档。** A/B 文档继续位于各自需求目录；不合成同一份任务图，也不把运行目录或锁纳入提交。
6. **运行合并后验证。** 重跑受影响单元、集成及必要端到端检查，特别检查两个需求共同修改的模块和接口；不能用各分支先前的 PASS 替代。
7. **报告集成结果。** 汇报目标提交、合并顺序、冲突处理、验证结果和剩余问题。推送、发布和删除 worktree 均不由本流程自动触发。

实施改造本身的验收合并在临时仓库演练；用户真实项目的目标分支不会因为执行测试而被合并或推送。
