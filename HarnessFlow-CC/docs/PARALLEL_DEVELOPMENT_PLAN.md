# HarnessFlow 项目并行开发改造方案

日期：2026-09-18  
状态：Draft  
范围：同一个 Git 项目中的多个独立开发需求并行推进  
本文只定义改造方案；文中的新参数、脚本和行为尚未实现。

## 1. 目标与假设

开发 A 与开发 B 各自拥有需求、设计、计划、任务图和进度，能够同时执行，并在完成后合并到同一个项目。

本方案采用以下假设：

- A、B 是两个独立开发流程，不是同一任务图里的两个任务。
- A、B 可能修改相同源码，因此需要分别拥有工作目录、分支和 Git 暂存区。
- 继续使用现有设计、规划、执行三阶段流程，以及阶段内部的 worker 并行机制。
- 首版由用户使用 Git 创建 worktree，在相应目录启动会话；HarnessFlow 负责识别、校验和隔离流程。
- 本轮只产出方案，不修改当前命令、skill、hook 或用户正在运行的项目。

成功标准：两个流程同时运行时，互不覆盖文档、运行状态和提交内容；其中一个暂停、失败或恢复，不改变另一个流程的执行边界。

## 2. 当前问题与依据

| 位置 | 当前行为 | 并行影响 |
| --- | --- | --- |
| [hf-design.md](../.claude/commands/hf-design.md)、[hf-plan.md](../.claude/commands/hf-plan.md) | 向固定的 `docs/harnessflow/` 写文档 | B 可能覆盖 A，或将 A 的文档当成续作输入 |
| [hf-run.md](../.claude/commands/hf-run.md)、[hf-status.md](../.claude/commands/hf-status.md) | 读取同一份任务图与状态账本 | 执行、恢复和查询无法区分需求 |
| [hf_scope_guard.py](../.claude/hooks/hf_scope_guard.py) | 读取 `.git/harnessflow/active_scope.json` | 两个会话会覆盖或清除彼此的批次范围 |
| [hf-phase-orchestrator.md](../.claude/agents/hf-phase-orchestrator.md) | 共享运行预算路径、交付路径和清理目标 | 一个阶段收尾可能影响另一个流程 |
| [install.sh](../install.sh) | 假定 `.git` 是目录，安装自检临时改写实际 scope 文件 | linked worktree 不兼容；运行期间安装可能干扰守卫 |
| [test-coverage-report.js](../scripts/test-coverage-report.js)、[run-sensors.py](../scripts/run-sensors.py) | 使用固定文档路径或报告路径 | 可能校验错误的需求，或覆盖同名报告 |
| [hf-verifier.md](../.claude/agents/hf-verifier.md) | 根据当前工作树的整体 diff 判断改动归属 | 同一个工作目录里的独立会话会互相污染验证结果 |

现有“批内任务路径不相交”的规则，只协调同一个编排器派出的任务，无法协调两个独立编排器。

Git worktree 中的 `.git` 通常是指向实际 Git 目录的文件。仅创建 worktree，而不修正运行路径解析，仍然不能可靠运行当前版本。

## 3. 方案决策

采用三项配套改造：

1. **需求文档按 `feature_id` 分目录。** 避免运行期间和最终合并时发生同名文档冲突。
2. **独立需求在独立 worktree 和分支中执行。** 隔离源码、暂存区、HEAD 和验证基线。
3. **运行状态按 worktree 隔离，写入会话互斥。** 防止在同一个工作目录误启动第二个编排器。

首版不实现跨需求调度器、自动合并器、自动创建或删除 worktree，也不支持在同一个工作目录同时运行两个写入流程。需求间如果存在接口依赖，应先确定共同基线，或等待上游合入后再开展下游工作。

只需要并行讨论设计的需求，也沿用同样的目录和会话约束，避免引入第二套并发规则。

## 4. 文档与标识

### 4.1 目录结构

```text
docs/harnessflow/
├── SENSOR_CHECKLIST.md             # 公共规则，不随需求复制修改
├── playwrightmcp-README.md          # 公共使用说明
├── feature-a/
│   ├── 00_REQUIREMENTS.md
│   ├── 01_DESIGN.md
│   ├── 02_IMPLEMENTATION_PLAN.md
│   ├── 03_TASKS.json
│   ├── 04_STATE.md
│   ├── prototypes/
│   ├── deliverables/
│   ├── handoffs/
│   ├── reports/                    # sensor 报告、验证附件
│   ├── LESSONS-P01.md
│   └── FINAL_REPORT.md
└── feature-b/
    └── 同样的流程目录
```

模板作为安装资源保留在 `templates/`，由创建需求的步骤复制。安装本身不再在文档根目录生成一套正在开发的 `00` 至 `04` 文件。

现有公共说明、增强方案等文件不应在迁移时被误判为某个需求的产物。

### 4.2 标识规则

- `feature_id` 在项目中标识一个独立需求，使用稳定的小写英文、数字和连字符，例如 `user-login`、`order-export`。
- 创建后不随分支重命名自动改变；不使用时间戳或当前分支名进行隐式推断。
- 限制长度和字符集，拒绝路径分隔符、`..`、Windows 保留名称，以及 `deliverables`、`handoffs`、`prototypes` 等已有公共目录名。
- 现有 `REQ-001`、`P01`、`P01-T01` 等编号保持不变，唯一性范围改为需求内部；跨需求引用必须带 `feature_id`。
- 任务图新增顶层 `feature_id`，文档头部记录 `Feature:`。读取时校验它们与所选目录一致。

`allowed_paths` 继续以当前工作树根目录为基准，例如 `src/api/**`，不能统一改成相对于需求文档目录。`deliverable`、设计附件和报告等流程产物则必须落入本需求目录。

## 5. worktree 与运行状态

### 5.1 目录解析

统一通过 Git 查询实际路径：

```text
WORKTREE_ROOT = git rev-parse --show-toplevel
GIT_DIR       = git rev-parse --absolute-git-dir
COMMON_DIR    = git rev-parse --path-format=absolute --git-common-dir
HF_DOCS       = WORKTREE_ROOT/docs/harnessflow/<feature_id>
HF_RUNTIME    = GIT_DIR/harnessflow/features/<feature_id>
```

`GIT_DIR` 是当前 worktree 的私有 Git 目录。`COMMON_DIR` 由所有 worktree 共享，只用于下文按需求建立的互斥记录，不用于保存 scope、预算或进度。

命令从子目录启动时也先解析并使用工作树根目录。Git 不可用、Git 版本不支持所需参数，或者解析结果无效时，明确报错，不退回一个猜测的路径。

### 5.2 运行文件

```text
<GIT_DIR>/harnessflow/
├── context.json                    # 当前 worktree 绑定的 feature_id
├── writer.lock/                    # 当前工作目录的写入所有权
└── features/<feature_id>/
    ├── active_scope.json
    ├── budget.json
    ├── models.json
    └── logs/

<COMMON_DIR>/harnessflow/feature-locks/
└── <feature_id>.lock/               # 防止同一需求在两个 worktree 同时写入
```

`context.json` 只保存本地绑定信息，不作为进度事实来源，也不写入 Git。项目中不设置共享的 `current_feature` 文件。

模型模式和预算在首次绑定时明确初始化；新 worktree 不会自动继承其他 worktree 未被 Git 跟踪的配置。允许显式复制配置，但不能复制 `active_scope.json` 或锁。

### 5.3 写入互斥与生命周期

- 所有会写文档或代码的入口，包括 design、plan、run、迁移和安装更新，都必须检查写入所有权。
- 每次写入命令先按固定顺序取得本 worktree 的锁和该需求的锁，再绑定上下文、修改文件。获取第二个锁失败时，仅撤销本次刚获取的第一个锁。
- 锁使用原子创建目录等系统操作获取，不能用“先检查不存在、再普通写文件”的方式实现。
- 锁内记录 `feature_id`、工作树路径、分支、会话标识、运行标识和开始时间。同一所有者派发的子代理共享这次授权，第二个顶层写入会话被拒绝。
- 清理 scope 和释放锁必须核对所有者与本次运行标识，不能按文件名直接删除另一个执行实例的状态。
- 正常结束、等待人工处理或可控失败时，先等待所有子代理停止写入，记录状态，再清理本次 scope 并释放锁。需求绑定保留，供后续恢复。
- 异常中断留下的锁不因“存在时间较长”自动失效。恢复时先确认原会话及子代理已停止，再显式接管；无法确认时拒绝抢占。

PID 和时间戳仅是诊断信息，不能单独证明旧会话已经结束。`hf-status` 为只读入口，不获取写锁，并显示运行中或残留锁的信息。

## 6. 命令与上下文传递

### 6.1 拟定用法

采用显式选项，保留 `/hf-run P03` 的阶段参数语义：

```text
/hf-design --feature feature-a "实现功能 A"
/hf-plan --feature feature-a
/hf-run --feature feature-a
/hf-run --feature feature-a P03
/hf-run --feature feature-a P03+
/hf-status --feature feature-a
```

参数解析必须处理完整参数串及带空格的目标描述，不能继续仅依赖 `$1`。各入口的 `argument-hint` 与允许调用的辅助工具同步更新。

### 6.2 选择规则

1. 显式传入 `--feature` 时使用指定需求，并检查当前 worktree 绑定和锁。与已有绑定冲突时明确报错，不自动切换正在使用的需求。
2. 未传参数但已有本地绑定时，使用该绑定。
3. 没有绑定，且只有旧版根目录结构、没有新式需求目录时，允许按第 9 节的旧版兼容规则运行。
4. 其他情况下要求明确指定需求；即使扫描到多个候选，也不按最近修改时间或聊天历史选择。

首次创建需求目录必须防覆盖；目录已存在时按恢复或编辑既有需求处理，不能重新初始化任务图和状态。切换一个已经绑定的工作目录需显式解绑，且工作区和运行状态必须满足退出条件；并行开发优先直接使用另一个 worktree。

### 6.3 子代理任务包

主会话向阶段编排器、worker、verifier 和 explorer 传递：

- `feature_id`、工作树根目录、需求文档目录、运行状态目录。
- 阶段及任务编号、当前运行标识、验证所需的起始提交。
- 与该角色相关的只读输入路径、允许写入范围和输出路径。

子代理不能自行切换需求，不能根据仓库里找到的第一份 `03_TASKS.json` 开始工作。返回摘要包含 `feature_id`，主会话复核一致后才能接受结果。

跨阶段继续使用独立子代理上下文；人工批准、独立验证和失败重试规则保持现有语义。

## 7. hook、辅助脚本与提交边界

### 7.1 统一路径解析入口

新增一个小型共享模块，例如 `.claude/hooks/hf_context.py`，供 Python hook 导入，并提供命令行方式输出解析后的上下文。命令、安装器与其他语言的脚本使用同一解析结果，避免各自拼接 `.git` 路径。

路径必须正规化后校验归属。测试需要覆盖空格、中文目录、Windows 路径，以及符号链接或 junction 导致的越界。

### 7.2 hook 改造

- scope 从当前 worktree 和需求对应的 `HF_RUNTIME` 读取，并校验其中的需求和运行标识。
- 将任务图、状态账本的保护扩展到所有新式需求目录，同时覆盖旧版路径；其他需求目录默认不可写。
- 取消当前对 `.git/harnessflow/` 的宽泛放行。由受控辅助入口维护运行状态，并明确编排层与 worker 的权限差异。
- linked worktree 的私有 Git 目录通常在工作树之外：仅对经过解析和所有权校验的运行文件提供有限操作入口，不放开任意仓库外写入。
- 执行批次需要 scope 时，缺失、损坏或标识不匹配必须阻断；design、plan 等不需要批次 scope 的状态要显式区分。

实施前需要用实际 Claude Code hook 事件验证：能否可靠识别顶层会话及子代理归属，如何传递运行标识，以及子代理失败时如何结束授权。不能把未验证的环境变量继承或模型自报角色当成可靠授权。

这是第一阶段的技术验证门槛。无法可靠建立所有者关系时，先解决绑定机制，不宣称已经支持多个写入会话的安全协调。

现有 hook 对 Bash 的检查主要是危险命令匹配，不能证明任意 shell 命令都遵守文件写入边界。本次仍以防止流程误操作为目标，依靠独立 worktree、入口互斥及独立 diff 验证共同约束；不把它描述成操作系统级沙箱。

### 7.3 检查脚本与安装器

| 文件或范围 | 拟改动 |
| --- | --- |
| `scripts/validate-ears.sh` | 保留文件参数，命令端显式传入当前需求的需求书路径 |
| `scripts/test-coverage-report.js` | 接受解析后的需求文档目录，移除对根目录固定任务图的依赖 |
| `scripts/run-sensors.py` | 区分源码根目录与需求报告目录，报告写入本需求的 `reports/` |
| `.claude/agents/hf-*.md` | 统一使用任务包上下文；报告、交接、经验记录和截图均定位到当前需求 |
| `.claude/skills/harnessflow/SKILL.md`、`MODELS.md` | 补充标识、目录、锁和恢复契约，更新配置路径 |
| `install.sh` | 支持普通仓库和 linked worktree；安装实际依赖的 `scripts/`、`templates/`；保留已有文件不覆盖规则 |
| 安装自检 | 在独立临时仓库验证守卫，不临时替换正在使用的 `active_scope.json`；活动工作目录拒绝更新 |
| `README.md`、`USAGE.md`、模板与示例 | 更新新项目用法、迁移方式、worktree 前置条件和恢复说明 |

公共传感器清单、模板等通过独立公共资源路径读取，不能将所有出现的 `docs/harnessflow/` 机械替换成需求目录。

### 7.4 验证与提交

- verifier 在指定 worktree 中运行，只使用本需求的任务图、验收条件和验证证据。
- 检查范围包括已暂存、未暂存和未跟踪的文件，避免只检查 `git diff` 而漏掉新文件。
- 源码变更按任务 `allowed_paths` 核对；编排层的文档和报告按独立的产物规则核对，不给 worker 开放整个文档目录。
- Git 提交继续由主会话完成。只暂存本需求已验证的代码和产物，不使用无范围的全仓暂存掩盖额外改动。
- 提交信息包含需求和阶段，例如 `feat(feature-a): P01 ...`；继续保留实现与状态分开提交的现有约定。
- 合并 A、B 后在集成分支重新运行受影响的验证。两个分支各自通过测试，并不等于合并结果通过测试。

## 8. 用户操作流程

以下为完成改造后的示例，不表示当前版本已经支持这些行为。

1. 在共同基线中安装新版 HarnessFlow 并提交安装文件。确认创建 worktree 所用的提交已包含 skill、命令、hook、脚本和模板。
2. 从约定基线创建两个不同分支的 worktree，例如在 Git Bash 中执行：

   ```bash
   git worktree add ../project-feature-a -b feature/a <base-commit>
   git worktree add ../project-feature-b -b feature/b <base-commit>
   ```

3. 分别在两个目录启动会话，A 使用 `--feature feature-a`，B 使用 `--feature feature-b`。
4. 各自完成设计批准、规划批准、执行和验证；需要暂停时保留本需求账本，下次从同一 worktree 恢复。
5. 分别审查并合并成果。两个需求的流程文档按独立目录保留，不在合并时改回同一套文件。

开始时已有 A 的未提交改动，不能假设创建 worktree 会自动带过去。应先确定 A 的保留位置和 B 的起点；不自动 stash、清理或搬走原工作区改动。

worktree 不隔离端口、数据库、外部服务和显式共享的缓存。若测试或开发服务会并发使用这些资源，需求计划需声明各自的端口、数据库或测试资源名；本次不新增通用资源调度器。

## 9. 旧项目兼容与迁移

### 9.1 兼容规则

- 纯旧版项目可以继续识别根目录的 `00` 至 `04` 文档，但仅按单工作目录、单流程模式运行。
- 路径解析与写入互斥仍使用新版实现，避免兼容入口绕过新规则。
- 旧式文档与新式需求目录同时存在时，必须显式选择已迁移需求或执行迁移，不能自动混读两套状态。
- 新创建的需求一律使用新目录，不再生成第二套根目录流程文件。

### 9.2 迁移步骤

1. 停止旧会话及所有子代理，检查 Git 状态、未提交改动和旧 scope；不在旧版本仍运行时升级。
2. 用户明确指定原流程对应的 `feature_id`。生成迁移清单：将复制的文档、附件、报告，以及需要重写的路径引用。
3. 确认目标需求目录不存在或为空，先保留可恢复的原文件副本，再按清单复制。
4. 只迁移流程产物，不迁移公共清单和独立项目方案。更新任务图中的 `feature_id`、文档元信息、交付路径和内部引用。
5. 针对 `context.read_first`、`allowed_paths`、`expected_outputs`、`verify` 中的旧路径逐项处理。源码路径不变，不对整个 JSON 或 Markdown 做无差别字符串替换。
6. 保持原始中文内容、任务编号、完成状态和已有批准结果；所有写入使用 UTF-8 无 BOM。仅改变存放位置不能把已完成任务重置为待办。
7. 运行结构和引用检查，按验证证据核对任务状态；迁移记录包含源、目标、改动清单和检查结果。
8. 显式建立 worktree 绑定，并确认新版入口只读写新位置。旧副本用于恢复，不继续参与执行；后续归档或删除单独处理。

`active_scope.json` 和旧锁不能复制进新运行目录。预算与模型配置可在确认来源后导入；运行中的任务需按现有证据重新核对，不通过搬运运行文件假装恢复成功。

### 9.3 回滚

迁移失败时停止新流程，保留迁移清单和原副本，不清理用户代码。确认没有写入会话后撤销本次绑定，并回到原文档位置。

新版本已经继续产生任务或代码变更后，不能直接恢复旧账本覆盖新状态。需先核对增量和 Git 历史，再决定恢复点；回滚不会自动执行 `git reset --hard`。

## 10. 分阶段实施

| 阶段 | 内容 | 验证与完成条件 |
| --- | --- | --- |
| P1：上下文与所有权验证 | 明确命令语法、路径契约；实现共享解析与锁的最小原型；验证真实 hook 会话及子代理身份 | 临时普通仓库和两个 linked worktree 得到不同运行目录；并发争抢只有一个所有者；子代理归属可核对 |
| P2：需求文档隔离 | 改四个命令、共享契约、模板和子代理任务包；让辅助检查脚本接收路径 | A、B 可独立设计和规划；使用相同阶段编号时文档、报告仍互不覆盖；错误需求选择被拒绝 |
| P3：执行与 hook 隔离 | 接入 scope、预算、模型配置、受控状态更新、恢复和清理；适配 verifier 与提交 | 两个 worktree 同时执行；A 的结束和失败都不改变 B 的 scope、锁及状态；同工作树第二写入会话被拒绝 |
| P4：安装与迁移 | 更新安装器、自检、旧项目兼容、迁移流程和使用文档 | 在 linked worktree 安装成功；已有文件不被覆盖；迁移保留编号、内容、批准与进度；异常可恢复 |
| P5：端到端验收 | 使用同一基线的 A、B，完成设计、规划、执行、中断恢复与合并验证 | 第 11 节必需场景全部通过，形成可复现的验证记录 |

阶段按 P1 → P2 → P3 → P4 → P5 推进。P2 完成只代表文档支持多需求；P3 和端到端验收完成前，不将新版标为支持并行开发。

## 11. 验收矩阵

| 场景 | 必需结果 | 验证方式 |
| --- | --- | --- |
| 两个需求使用相同 REQ、阶段和任务编号 | 输入、交付和报告均归属正确 | A、B 同时生成并校验一套最小流程 |
| 普通仓库与 linked worktree | 路径解析正确，`.git` 为文件时可正常运行 | 真实临时 Git 仓库与两个 worktree 集成测试 |
| 双 worktree 同时修改同一源码相对路径 | 各自 diff、文件内容和提交独立 | 并行运行两组最小实现与独立验证 |
| 同 worktree 两个写入会话 | 第二个在任何文档、scope 或绑定写入前被拒绝 | 并发获取所有权，检查文件未被后到会话改变 |
| 同需求在不同 worktree 重复启动 | 仅一个取得该需求写入权 | 并发竞争需求锁 |
| 主会话派生子代理 | 继承正确需求和授权，不被当作第二顶层写入者 | 使用真实 hook 事件验证主会话与子代理 |
| A 完成或进入人工等待，B 继续运行 | A 仅清理自己的运行文件；B 的范围与所有者不变 | 清理前后比较 B 的状态及范围检查结果 |
| 异常退出与恢复 | 不自动抢锁、不接受无证据的完成状态、不删除其他所有者文件 | 模拟中断、残留锁及重新接管 |
| scope 缺失、损坏或需求不符 | 批次执行阻断并给出明确原因 | 注入错误状态；同时验证设计阶段可正常工作 |
| 跨需求文档、Git 内部及仓库外写入 | 普通写工具被拒绝，受控编排操作只作用于授权目标 | 扩展现有 scope guard 测试 |
| 含中文、空格及链接目录的路径 | 正确解析；链接外逃被拒绝 | Windows 路径用例及链接边界用例 |
| 缺少需求参数且没有绑定 | 不猜测、不覆盖；给出明确选择提示 | 空项目、多需求目录和混合旧版目录用例 |
| legacy 迁移与中途失败 | 中文内容、编号、状态和批准保留；原副本可恢复 | 迁移前后结构、内容和引用比较，故障注入 |
| 安装与重复安装 | 不覆盖现有配置；不触碰活动 scope；依赖脚本齐全 | 普通仓库、linked worktree、活动会话三种安装测试 |
| A、B 合并 | 两套文档保留，代码冲突显式处理，集成验证通过 | 临时集成分支进行合并及验证 |

保留现有 scope guard 回归用例。新增测试针对真实边界和并发结果，不只断言路径常量被替换。运行 Python 测试前，先验证解释器与用户激活的环境一致。

## 12. 交付清单

- 支持需求目录的四个入口命令、共享 skill 契约和子代理定义。
- worktree 路径解析、写入所有权与 scope 生命周期的实现及测试。
- 接受明确输入、输出路径的验证脚本与报告生成脚本。
- 支持 linked worktree 的安装器、自检及完整模板资源。
- 旧项目迁移与回滚说明，以及 A、B 并行开发操作示例。
- 覆盖并发、恢复、隔离和合并的验收记录。

本方案完成后的支持边界是：一个需求对应一个活动 worktree，一个 worktree 同时只有一个写入编排器，编排器内部按现有批次规则并行派发任务。
