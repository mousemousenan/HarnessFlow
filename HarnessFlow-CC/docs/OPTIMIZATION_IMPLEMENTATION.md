## 2. 开工条件与计时口径

### 2.1 开工检查

1. 记录分支、HEAD、工作区差异和五个目标文件的基线，保留已有未提交内容；已具备的规则只补差异，不重复追加章节。
2. 确认实施目录和测试项目目录。当前项目位于更大的 Git 仓库内，不能把本项目目录直接当作 Git 根目录；运行验收使用独立临时 Git 项目，避免向父仓库 `.git/` 写入运行状态。
3. 本轮不包含并行开发方案中的 worktree/多需求隔离。在测试项目中保持一个主会话、一个活动阶段编排器和一个台账写入者。
4. 在目标 Claude Code 会话实测可用的定时唤醒、任务状态查询、停止与取消定时任务能力，记录实际工具名和权限要求。`ScheduleWakeup`、`CronCreate`、`TaskStop` 是源提案给出的候选，不能仅凭名字假定可用。
5. Python 或测试执行前，先验证解释器：

   ```text
   python -c "import sys; print(sys.executable)"
   ```

   核对与用户激活的 Conda 环境一致后，再运行现有回归基线：

   ```text
   python -m unittest discover -s tests -p "test_scope_guard.py" -v
   ```

6. 仅编写本文不启动 `/hf-run`，不创建定时任务，不停止任何现存代理。后续故障演练只针对测试项目创建的实例。

### 2.2 明确计时含义

源提案同时出现“挂掉之后 ≤20 分钟自动发现”“每 20 分钟检查、连续两轮异常”和“≤40 分钟发现”三种表述，不能同时作为保证。本文保留草案参数，采用以下可检查口径：

| 指标 | 本轮实施口径 |
| --- | --- |
| 轮询间隔 | 主会话每 20 分钟唤醒一次，使用会话级任务，避开整点集中触发 |
| 活动窗口 | 检查近 20 分钟的本次执行活动，或本实例仍持有的验证子进程 |
| 心跳新鲜度 | 当前实例最后一条有效心跳年龄 ≤40 分钟 |
| 停滞确认 | 连续两轮不健康；任一健康轮次将异常计数清零 |
| 实际处置时延 | 从最后真实活动至确认停滞单独计时，包含活动窗口、轮询相位和调度延迟，不直接写成 ≤20 或 ≤40 分钟 |

例如，最后活动在 00:00，00:20 检查时仍处于窗口边界，00:40 首次异常、01:00 第二次异常，则确认耗时约 60 分钟。仅心跳过期触发时，等待还可能更长。

**原提案的“≤20 分钟发现”目标在此参数下尚未满足。** 验收需单列该差距；若该目标被要求作为硬门槛，须先调整源提案的检查周期与确认阈值，不能通过改写验收结论消除差距。损失收敛到分钟级也需实际中断证据支撑，本轮不增加更高频的代码检查点机制。

调度依赖主会话能够被唤醒并执行检查；若主会话本身也受同一 API 故障阻塞，此方案不提供独立于模型服务的定时保证。

## 4. OPT-01：O3 心跳与机械恢复

修改 `hf-phase-orchestrator.md`、`SKILL.md` 和 `hf-run.md`。先确定台账，再让后续两项使用同一协议。

### 4.1 台账协议

路径：`.git/harnessflow/phase_ledger.jsonl`。UTF-8 无 BOM，每行一个 JSON 对象，每条序列化后的记录不超过 500 字符，保留源提案的五个字段：

```json
{"ts":"2026-09-18T10:00:00+08:00","phase":"P06","batch":"P06-B1","step":"verify_command_done","detail":"P06-T01 cmd=1 exit=0 log=.git/harnessflow/verify-logs/P06-T01.log"}
```

- `ts` 使用带时区的 ISO 8601 时间；示例 ID 仅说明格式，不表示当前项目存在该任务。
- `step` 使用固定事件名，任务 ID、结果和关键产物路径放入 `detail`；长命令和完整输出放日志，台账只给索引。尚未进入批次的阶段事件将 `batch` 记为空字符串，不填入旧批次。
- 仅活动阶段编排器追加；worker、verifier 和看门狗不直接写台账。并行 worker 的返回由编排器统一记录，可按实际返回顺序写入。
- 只追加，不清空历史，不改写已完成记录。一次追加一条完整 JSON 和换行，控制字符按 JSON 转义。
- 台账属于运行基础设施，不放进任务 `allowed_paths`；台账记录不是任务完成证据，也不是 `04_STATE.md` 的替代品。

### 4.2 写入点

| 事件 | 写入时机与必要内容 |
| --- | --- |
| `scope_written` | 本批 scope 成功写入后；记录批次和 scope 路径 |
| `worker_dispatched` | 派发成功后；记录任务 ID、实例标识和本阶段累计派发数 |
| `worker_returned` | 收到返回后；记录任务 ID、PASS/FAIL/BLOCKED/HUMAN_BLOCKER 及证据位置 |
| `verifier_dispatched` | verifier 派发成功后；记录批次和提交给它的证据路径 |
| `verify_command_done` | 命令结束且日志收口后；记录任务、命令序号、退出码及日志路径 |
| `deliverable_written` | 交付文档成功写入后；记录路径 |
| `scope_cleared` | 本批或阶段 scope 确认清理后 |
| `phase_summary_ready` | 返回摘要准备完成时；记录摘要结果与交付路径 |

源提案允许更细事件，补充以下三个以支持恢复和长时等待：

- `phase_started`：编排器启动时立即写入，`detail` 含当前后台任务标识及第几次尝试，建立本次记录边界。
- `verifier_returned`：记录独立验证结论和完整证据位置，区分“已派验证”和“验证已完成”。
- `command_running` 或 `waiting`：超过一个轮询周期的工作，编排器以可返回控制权的等待方式，每不超过 20 分钟检查自身持有的任务/命令，并记录所等对象及真实状态；不能由看门狗代写以制造活性。

若宿主的命令或 Agent 调用在长时间等待中不能返回控制权，需在 OPT-00/OPT-04 记录限制；未解决前不能宣称覆盖长时健康任务的防误杀要求。进程存在只说明仍存活，不证明业务持续推进，也不替代命令自身的超时约束。

### 4.3 主会话复核与恢复

在 `hf-run.md` §3.2 派发时记录本次阶段、后台任务标识、尝试次数、台账起始位置；这些是现有状态账本中的运行记录，不新增摘要字段。读取时先按本次实例边界和阶段筛选，再从尾部定位；最后 N 行不足以覆盖全部未完成任务时继续向前读取，不能只取文件末行。

`hf-run.md` §3.3 增加：台账显著步骤是否完整、是否与摘要和独立验证证据一致。首次遗漏心跳记入 LESSONS；若同时缺少验证证据，仍不能接受 PASS。

`SKILL.md`“状态与恢复”及 `hf-run.md` §4 使用统一恢复顺序：

1. 确认旧实例及其写入者已停止，按 §6 清理属于旧实例的 scope。
2. 读取当前尝试的台账，按任务重建“已派发、已返回、已取证、已独立验证、待收尾”状态。
3. 根据台账指向读取必要日志、交付和 verifier 结论，保留既有 `git status`、HEAD 与路径归属核对。正常路径不靠文件 mtime 推断业务进度。
4. 将下列简报交给全新编排器，只做剩余动作；证据缺失的任务重新取证或验证，不把 worker PASS、命令 exit 0、产物存在直接转换成 `done`。

```text
阶段 / 批次：<ID>
上次实例 / 尝试：<实例标识、次数、台账边界>
最后可靠事件：<ts、step、detail>
已通过独立验证：<任务、结论与证据路径>
已实现但待验证：<任务、已有日志与缺失证据>
尚未执行 / 待收尾：<任务或动作>
预算：<阶段重派已用次数、worker 已用数量、任务修复已用次数>
下一步：<从哪个动作恢复>
缺口：<未知状态或证据不足，或 NONE>
```

台账不存在、损坏或记录与产物不一致时，明确标记“台账恢复不可用”，按现有保守恢复规则核对证据，记录退化原因；不能编造中断点。尾部半行保留原状，读取前一完整有效行；恢复追加前，若文件末尾没有换行，先只追加换行隔离残行，再追加新实例的完整事件。读取时跳过损坏行并记录退化原因，确保后续 `phase_started` 可独立解析。旧阶段记录、未来时间、缺时区或无法识别的记录不能作为当前实例新鲜心跳。

对于“动作完成、事件未写”的窗口，先核对台账指向的产物和任务预期输出。存在实现产物时优先补验证，不能仅因缺事件就全部重做；没有证据支持的不可重复操作须报告不确定性。

**OPT-01 验收：** 所有必要事件可解析且可归属；并行返回可还原；正常恢复简报由台账索引生成；缺失和截断台账走明确退化分支；完成判定仍依赖独立验证。

## 5. OPT-02：O2 确定性 verify 直跑

修改 `MODELS.md`，同步 `SKILL.md` 中 verify 的取证说明、编排器“验证每批”、verifier“独立重跑 verify”及 `hf-run.md` 的批内验证描述。

### 5.1 适用范围和职责

- 只在 `single_model` 模式启用。`multi_tier` 继续由 verifier 独立重跑原有命令。
- worker 自测仍只是建议。worker 完成后，由阶段编排器重新执行任务定义中的确定性、非交互 verify；主会话不运行这些业务测试。
- pytest、lint、typecheck、build 和有明确预期退出码的脚本可直跑；需要语义判断、交互操作或人工授权的步骤保留对应原流程，不因“有退出码”就直接宣布通过。
- 编排器提供原始证据，独立 `hf-verifier` 判定 acceptance、范围归属、产物内容、测试充分性和 Sensor 结果。每批仍需独立 verifier PASS 才能推进。

提案中的“hf-verifier 仅做 acceptance”在当前流程中解释为“保留实质判定职责、免除合格证据对应的重复取证”，不能删掉 Adequacy Review、Sensor、UI 证据检查或内容抽查。

### 5.2 直跑与日志步骤

1. 取得本批 worker 完成后的稳定代码状态，记录 HEAD、实际改动基线和任务定义中的命令；取证期间不允许 worker 继续写入。
2. 在任务要求的工作目录和解释器环境运行原命令，不降低测试范围，不把命令改成始终成功的形式。
3. 将 stdout/stderr 和执行元信息写入 `.git/harnessflow/verify-logs/<任务ID>.log`。同任务多命令、修复重跑和阶段重派使用追加段落，标明尝试与命令序号，不覆盖旧证据。
4. 每段包括：阶段/批次/任务、当前实例和尝试、命令原文、工作目录、代码基线、开始/结束时间、原始退出码。使用管道时保留被测命令的退出码，不能拿 `tee` 的退出码代替。
5. 日志成功收口后追加 `verify_command_done`。中断、超时、命令不可用或写日志失败均如实记录；只有开始没有结束的日志不能算命令完成。
6. 将命令列表、日志段落定位、代码基线、验收条件、预期产物和 diff 清单交给 verifier。完成取证后若实现变化，受影响证据失效，需重新取证。
7. verifier 返回后，由编排器将其任务级结论原样追加到对应任务日志的“独立验证结论”段，注明验证实例和时间，与原始命令输出分开；随后写 `verifier_returned` 指向该段。阶段收尾再将结论汇入交付文档，保证收尾前中断也能找到判定证据。

由 verifier 独立打开原始日志，核对命令、任务、尝试和当前改动。日志缺失、截断、过期或无法归属时重新取证或判证据不足，不采信编排器一句“测试通过”。预期非零退出码按任务定义判断；命令找不到、依赖缺失等不能伪装成符合预期的业务失败。

### 5.3 现有 Sensor 行为的处理

[run-sensors.py](../scripts/run-sensors.py) 会按项目类型运行测试和 lint，正常生成报告后返回 0，即使报告内存在 `fail`。因此：

- 脚本退出码只证明脚本执行结果，Sensor 是否通过必须读取报告内容并由 verifier 判定。
- 本轮保留现有 Sensor 流程及必要报告；它可能再次运行测试，不能声称已经消除所有重复命令。
- 本轮不修改 Sensor 脚本或增加证据复用接口。优化收益以实际减少的重复取证调用衡量，不把源提案的“API 暴露面减半”当成未测量即可成立的结论。

**OPT-02 验收：** 编排器直跑日志完整可追溯；verifier 仍独立判定全部验收；失败、失效或缺失证据不能放行；多模型原路径保留；Sensor 的内部失败不会被 exit 0 掩盖。

## 6. OPT-03：O1 主会话看门狗

共享判定写入 `SKILL.md`；在 `hf-run.md` §3.2 后增加派发后看门狗小节，并接入 §3.3 复核、§4 中断处理和退出清理。

### 6.1 建立与只读检查

派出一个阶段编排器后创建一个会话级唤醒任务，绑定阶段 ID、当前后台任务标识、派发时间与本次台账边界。每次派发必须使用可被状态查询和停止的执行方式，记录实际定时任务 ID。`allowed-tools` 只补充 OPT-00 实测需要的工具，不照抄不存在的名称。

每轮先处理已完成/失败的终态；仍运行的实例同时满足以下条件才算健康：

1. 当前绑定的实例未失败、未被停止。
2. 近 20 分钟有归属于本次阶段执行的文件活动，或有该实例持有的 pytest/python 等验证子进程在运行。检查源提案列出的 `.git/harnessflow/`、台账、阶段 `allowed_paths` 涉及目录及 `docs/harnessflow/deliverables/`。
3. 当前尝试的最后有效心跳年龄 ≤40 分钟；恰好等于边界时按健康计算。

不能把其他项目的 Python 进程、旧阶段日志或看门狗自己写的检查记录当成执行活动。子进程归属需要宿主任务信息或可核验的父子进程关系，不能只匹配进程名。进程存在也不能豁免心跳检查；长时工作的续报按 §4.2 执行。

看门狗不修改源码、台账或运行中的 scope。检查结果由主会话记入运行记录：实际检查时间、实例状态、活动证据、最后心跳时间、异常计数和处理动作。

### 6.2 判定与生命周期

| 观察结果 | 处理 |
| --- | --- |
| 健康 | 异常计数清零，继续等待 |
| 第一轮不健康 | 记录可疑信号，保留实例，下次复核 |
| 连续第二轮不健康 | 按 §6.3 执行停滞处置 |
| 正常完成 | 取消本实例看门狗，再走摘要复核；完成通知本身不能直接标阶段 done |
| 明确 failed/killed/异常退出 | 不必等待两轮，走中断恢复规则并计入同一重派预算 |
| HUMAN_BLOCKER、预算用尽或最终失败 | 取消看门狗，记录状态和准确恢复条件，停止自动派发 |
| 过期唤醒仍到达 | 核对实例绑定，忽略旧实例回调，不影响后来派出的编排器 |

若定时唤醒不可用，记录 O1 未启用，不声称自动保护已生效；O3/O2 可以单独验证。停止或实例归属能力不足时，不执行自动清理和重派，记录人工恢复条件。此限制不能计为完整 O1 通过。

### 6.3 终止、清理与重派

顺序必须固定：

1. 再次核对目标仍是当前实例，排除刚完成和旧唤醒事件。
2. 停止该编排器，确认其派出的仍会写文件的 worker/命令也已停止。停止失败或无法确认时保留 scope，不启动新写入者。
3. 核对 `active_scope.json` 的批次属于被终止实例后，清理这一份残留；不得递归删除整个 `.git/harnessflow/`，不得删除台账和验证日志。归属不明时报告阻塞。
4. 取消旧看门狗，将中断证据、已用预算和重派计数写入现有状态账本。
5. 按 §4.3 生成恢复简报；仍有预算时派全新阶段编排器，并为新实例建立新的看门狗。

同阶段**最多重派 2 次**，初次派发不计在这两次中；摘要复核失败、异常退出和看门狗停滞共用同一计数。主会话恢复后从状态记录继承计数，不从零开始。

保留 `budget.json` 的现有字段和 `WORKER_SPAWNS` 摘要字段。worker 派发数量与任务修复次数也在恢复简报中继承，新编排器只消费剩余预算；台账有派发窗口缺口时保守核对宿主记录，不假定缺记录等于未消费。

**OPT-03 验收：** 仅目标实例被检查和停止；健康轮次清零；已停止写入后才清理并重派；所有终态取消看门狗；两次重派后仍失败即 blocked；旧回调和主会话恢复不会绕过预算。

## 7. OPT-04：验证与证据

### 7.1 静态核对

- 五个目标文件对取证、判定、恢复、计数和退出清理的说法一致，`hf-run.md` 真正调用共享规则；单模型例外不与无条件“verifier 必须自己重跑”冲突。
- 台账和日志不占用任务 `allowed_paths`，不扩展通用写权限；返回摘要字段、产品任务图和人工门规则保持不变。
- 文档为 UTF-8 无 BOM；源提案及已有中文保留；变更只涉及 §1.2 的实施文件和验收证据。
- 在环境核对通过后运行 §2.1 的 scope guard 回归，确认没有破坏现有范围约束；无需为纯规则文本增加测试框架。

### 7.2 运行验证矩阵

在独立测试项目执行。用受控样例先核对异常判定，再完成真实阶段与定时唤醒验证；手工伪造时间戳或缩短时间的演练不能替代真实 20 分钟唤醒证据。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| V01 | 单模型完整正常阶段，包含多命令 verify | 必要心跳齐全；原始日志完整；verifier 有独立结论；交付与摘要一致；scope、看门狗均清理 |
| V02 | 多模型阶段 | verify 沿用原有 verifier 重跑路径；O3/O1 可用；不误入单模型直跑分支 |
| V03 | 验证命令持续超过 40 分钟 | 编排器仍可续报；本实例子进程可归属；正常执行不被误杀；不能用任意 Python 进程代替证据 |
| V04 | 编排器实例存活但无活动、无心跳 | 连续两轮异常后停止旧写入者、清理 scope、全新上下文恢复；记录真实检测耗时 |
| V05 | 本实例无活动，但其他项目有 Python 进程或文件写入 | 外部活动不使当前实例恢复健康；子进程存在但心跳过期也不能永久豁免 |
| V06 | 一轮异常后恢复；时间戳处于 20/40 分钟边界；唤醒延迟 | 健康后计数归零；边界判定符合 §2.2；延迟如实计入测量 |
| V07 | 正常完成、人工门、明确失败、预算阻塞及旧回调 | 正确取消定时任务；旧回调不停止新实例；人工门不被自动续跑或代签 |
| V08 | 停止失败、worker 仍存活或 scope 无法确认归属 | 不先删 scope，不启动第二个写入者，返回明确恢复条件 |
| V09 | 看门狗重派与复核重派混合发生；主会话中途恢复 | 阶段重派共用上限 2；worker 和修复预算延续；超限停止 |
| V10 | 台账缺失、空文件、截断尾行、非法时间、旧阶段记录 | 不伪造活性或进度；保留有效证据；隔离残行后新实例事件可解析；明确退化恢复原因 |
| V11 | 产物已写事件未写；命令结束日志未收口；scope 已清理摘要未返回 | 区分实现、取证、判定和收尾；不无证据跳过验证，不自动重做已有实现 |
| V12 | 多条 verify、非零失败、预期非零、缺命令、管道及重试 | 保存真实退出码和完整尝试；不覆盖旧日志；按任务预期判断，基础环境故障不伪装成功 |
| V13 | 日志缺失/截断/过期；取证后代码变化；worker PASS 但验收失败 | verifier 要求重新取证或返回 FAIL；编排器不能自行放行 |
| V14 | Sensor 脚本 exit 0、报告含 fail；产物存在但为空壳 | 独立判定不通过，质量门禁保留 |
| V15 | 无定时/停止能力或长调用无法返回控制权 | 明确记为能力限制或未验证，不能将静态规则检查记为运行通过 |

测试不需要实际制造中转服务故障，可在临时项目控制任务停止响应和证据时间；终止目标始终是本次演练创建的实例，不操作用户现有会话。

### 7.3 证据记录与验收结论

`docs/optimization-evidence/VALIDATION.md` 至少记录：

```text
实施基线 / 目标文件差异：
测试项目 / 模式 / 阶段 / 宿主版本 / 实际可用工具：

命令 / 工作目录 / 开始结束时间 / 退出码 / 日志路径：
```

验收分开记录“规则已写入”“完整阶段通过”“异常恢复通过”和“时延目标达成”。一项通过不代替另一项；正常阶段未发生中断时，恢复指标为未验证，必须通过受控中断补验。证据需保留可访问副本或必要摘录，不能只引用已删除的临时目录。

只有 O3、O2、O1 的必要场景有真实证据，且明确披露 §2.2 的时延目标差距，才可报告本轮规则实施及其已验证范围。没有满足原始 ≤20 分钟目标时，不写“源提案全部目标已达成”。

## 8. 启用与回退

1. 按任务顺序修改规则，在测试项目验证后再用于下一个已批准阶段。O3 先启用，O2 随后，O1 最后；不在一个正在执行的阶段中途切换协议。
2. 首个真实阶段保留完整台账、验证日志及唤醒记录，按 §7 写出验证结论，再决定推广范围。源提案状态如需同步，必须根据实际证据更新，不能因本文完成就改成验证通过。
3. 看门狗误判时，先取消对应定时任务并保留现场；确认活动写入者状态后处理恢复，不直接清空运行目录。O1 可先停用，保留 O3/O2 的证据能力。
4. O2 证据链不可靠时，恢复 verifier 独立重跑命令；O3 记录不可靠时，恢复既有保守核对并披露恢复成本。独立判定和预算上限始终保留。
5. 回退只撤销本次五个规则文件中的对应修改，保留其他已有改动、台账、验证日志和状态记录；不用 `git reset --hard`、`git clean` 或删除整个运行目录回退。
