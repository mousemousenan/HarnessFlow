# 模型档位与单模型模式

`/hf-run` 在阶段循环前读 `.git/harnessflow/models.json`（不存在则按 `multi_tier` 处理）：

```json
{"mode": "single_model", "note": "GLM 中转，仅一个模型可用"}
```

`mode` 取 `multi_tier` 或 `single_model`。

## multi_tier（默认，Claude 官方端点）

按 skill 的档位规则走：任务的 `model` 字段传给 `Agent` 工具，`opus` / `sonnet` / `haiku`
分别对应重判断、常规实现、样板任务。

## single_model（第三方中转，只有一个模型可用）

端点只暴露一个模型时，档位区分没有意义。这时：

### 1. 不传 `model` 参数

派子代理时**省略** `Agent` 工具的 `model` 参数，让它继承主会话模型。

原因：`opus` / `sonnet` / `haiku` 是 Claude Code 的内部别名，解析时对着 Anthropic 的模型目录。
`Agent` 工具的 `model` 参数只接受家族别名，不接受完整模型 ID。走中转时传这些别名，
最好的情况是被映射层正确翻译，最坏的情况是静默落到一个你没打算用的模型上。
不传就没有这个风险。

任务图里的 `model` 字段照旧保留——它记录的是"这个任务需要多强的模型"这个判断，
换回官方端点时直接生效，不用重写任务图。

### 2. 修复不再"上调一档"

`multi_tier` 下失败任务重试时会上调一档。单模型下没有更高档，
**这条规则失效，不要假装执行它**。

替代做法：重试时改变的是**信息量**，不是模型。给新建的 worker 补上：

- 上一次的完整失败命令输出（不只是摘要）
- 上一次改动的 diff
- 一句明确的诊断方向：「上次的失败原因判断是 X，这次换 Y 思路」

同一方法连续失败两次后不要再派第三个 worker 重试——那只是用同一个模型重复同样的判断。
置 `blocked`，把证据交给人。这在单模型下比 `multi_tier` 下更早触发，是对的。

### 3. 验证仍然独立，但要知道它弱了一档

`multi_tier` 下 `hf-verifier` 用 `opus` 判 `sonnet` 写的代码，判定方比实现方强。
单模型下是同一个模型判自己写的代码——**独立性还在（全新上下文、只读工具、
依据原始退出码和日志判定），但"更强的模型复核"这一层没有了**。
确定性命令由编排器直跑取证（见第 5 条），verifier 读取原始日志，不再为合格证据重复跑命令。

后果：验证方对"测试是否真能捕获错误"这类需要判断力的检查，可靠性下降。
命令退出码这类客观证据不受影响。

所以单模型模式下这两件事必须做实：

- **`verify` 命令要更硬。** 不能只有 `pytest`，要有覆盖率门槛、类型检查、lint。
  客观闸门越多，越不依赖判断力。`/hf-plan` 在 `single_model` 下应主动加严 `verify`。
- **验收标准要更可判定。** 「接口行为正确」这种要人判断的条目，
  改写成能被命令验证的形式。改不了的，标 `human_gate` 交给人。

不要因为验证弱了就跳过它。弱化的复核仍然拦得住越界写入、缺失产物、命令失败——
这些占实际失败的大多数。

### 4. 上下文预算收紧

第三方中转的上下文窗口通常小于 Claude 官方模型。`hf-phase-orchestrator` 在
`single_model` 下要：

- 摘要更短，宁可指向交付文档也不在摘要里展开
- 任务包里的「设计约束摘录」只摘当前任务真正需要的段落，不整节复制
- 单个阶段的批次数超过 4 时，提示主会话考虑把该阶段拆成两个阶段

### 5. 确定性 verify 直跑

本条只在 `single_model` 启用。`multi_tier` 继续由 `hf-verifier` 独立重跑原命令。

确定性、非交互的 `verify`（pytest、lint、typecheck、build、有明确预期退出码的脚本）
由阶段编排器直接用 Bash 重跑取证，把 stdout/stderr 和执行元信息写入
`.git/harnessflow/verify-logs/<任务ID>.log`。这是取证，不是判定。
主会话不运行这些业务测试；worker 自测仍只是建议。

需要语义判断、交互操作或人工授权的步骤保留对应原流程，不因「有退出码」就宣布通过。

直跑步骤：

1. 取得本批 worker 完成后的稳定代码状态，记录 HEAD、实际改动基线和任务定义中的命令；
   取证期间不允许 worker 继续写入。
2. 在任务要求的工作目录和解释器环境运行原命令，不降低测试范围，
   不把命令改成始终成功的形式。
3. 同任务多命令、修复重跑和阶段重派使用追加段落，标明尝试与命令序号，不覆盖旧证据。
4. 每段包括：阶段/批次/任务、当前实例和尝试、命令原文、工作目录、代码基线、
   开始/结束时间、原始退出码。使用管道时保留被测命令的退出码，不能拿 `tee` 的退出码代替。
5. 日志成功收口后，编排器追加 `verify_command_done`。中断、超时、命令不可用或写日志失败
   均如实记录；只有开始没有结束的日志不能算命令完成。
6. 将命令列表、日志段落定位、代码基线、验收条件、预期产物和 diff 清单交给 `hf-verifier`。
   完成取证后若实现变化，受影响证据失效，需重新取证。
7. verifier 返回后，编排器将其任务级结论原样追加到对应任务日志的「独立验证结论」段，
   注明验证实例和时间，与原始命令输出分开；随后写 `verifier_returned` 指向该段。

`hf-verifier` 独立打开原始日志，核对命令、任务、尝试和当前改动，并继续做
Adequacy Review、Sensor、UI 证据、范围归属、acceptance 和产物抽查。
日志缺失、截断、过期或无法归属时重新取证或判证据不足，不采信编排器一句「测试通过」。
预期非零退出码按任务定义判断；命令找不到、依赖缺失等不能伪装成符合预期的业务失败。

Sensor 脚本退出码只证明脚本执行结束。`run-sensors.py` 可能在报告含 `fail` 时仍返回 0，
是否通过必须读取报告内容并由 verifier 判定。本轮不修改 Sensor 脚本。

## 怎么切换

```bash
mkdir -p .git/harnessflow
echo '{"mode":"single_model"}' > .git/harnessflow/models.json
```

换回官方端点时改成 `{"mode":"multi_tier"}` 或直接删掉这个文件。
任务图不用动。
