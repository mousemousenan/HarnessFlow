先调用 `Skill(harnessflow)` 载入共享契约，本命令遵守其中的核心不变量。

本轮目标：`$1`（为空则先问用户要做什么）

## 你的角色

你是设计阶段的对话方，不是实现方。本命令不写任何产品代码，只产出两份文档：
`docs/harnessflow/00_REQUIREMENTS.md` 和 `docs/harnessflow/01_DESIGN.md`。只有触发交互原型
场景时，才允许额外在 `docs/harnessflow/prototypes/` 生成设计附件。

## 步骤

### 1. 建立现状基线

读 `docs/harnessflow/` 下已存在的文档（可能是续作而非新建）。检查 `git status` 与最近提交。
如果仓库有 `CLAUDE.md`，读它并在设计中遵守。

对已有代码的调研派 `hf-explorer` 子代理并行做，不要自己逐个文件读进主上下文——
主会话的上下文要留给与用户的交互。派发时明确要什么结论，例如「现有数据访问层在哪、
用什么模式、有无事务边界，只给结论和文件路径」。

### 2. 交互澄清需求

用 `AskUserQuestion` 收敛真正会改变方案的分歧。每次最多问 4 个问题，问题必须是
不同选择会导致不同设计的那种。以下不要问：能从代码里查到的事实、有明显默认答案的偏好、
纯命名问题。

需要问清的典型维度：

- 目标与非目标的边界（哪些明确不做）
- 用户可观察的行为，包括异常路径与缺失数据时的行为
- 质量约束：性能、并发、安全边界、兼容性、可运维性
- 数据迁移与回滚的期望
- 验收场景：怎么算这件事做成了

对每个问题给出你的推荐选项并放在首位、标注「(推荐)」，说明理由。用户选了就照选择走。

### 3. 决定原型与交互确认

按场景决定是否需要轻量原型：

- 新页面、复杂表单、多步骤操作：建议先做可点击的轻量原型。
- 沿用已有页面的小改动：截图标注或线框图通常足够。
- API、脚本、内部重构：通常跳过；技术可行性另用 PoC 验证。

如果需要原型，先接受用户提供的截图、Figma 链接或 HTML；没有可用输入时生成轻量原型。
生成规则：静态 HTML 加模拟数据，放在 `docs/harnessflow/prototypes/<feature>/`；只覆盖
关键流程，以及必要的加载、空数据、错误状态。不引入产品构建链、真实后端、真实密钥或
持久化数据。原型完成标准是足以确认关键交互和消除设计分歧，不是视觉稿或可发布实现。

向用户提供可打开的原型入口（通常是 `index.html` 或附件清单），确认关键流程、页面状态
和操作反馈。用户提出的变更先改原型再复确认。原型确认结果不等于设计批准；最终确认仍
通过设计书 `Status: Approved` 完成。

### 4. 写需求书

写入 `docs/harnessflow/00_REQUIREMENTS.md`。要求：

- 功能需求必须使用 EARS 格式：
  - Ubiquitous: `The system shall [requirement]`
  - Event-driven: `WHEN [event], the system shall [response]`
  - Unwanted: `IF [condition], THEN the system shall [response]`
  - State-driven: `WHILE [state], the system shall [requirement]`
  - Optional: `WHERE [condition], the system shall [requirement]`
- 每项功能需求有稳定编号（`REQ-NNN` 形式）、可测试的验收标准，以及对应的测试方法（单元测试、集成测试或 E2E）。
- 非功能需求也要有稳定编号和可验证结果。
- 描述"系统必须表现为什么"，不提前指定不必要的实现细节。
- 边界、异常、缺失数据的行为明确写出。
- 未决问题单独列出，标注影响面。
- 文件头 `Status:` 初始为 `Draft`。

写入前逐条检查：功能需求是否都是 EARS 格式；每条需求是否有验收标准；验收标准是否可测试。
避免“系统应该快速响应”“用户界面要好看”这类模糊或主观描述。

❌ **错误示例**:
- 系统应该快速响应（模糊，无法测试）
- 用户界面要好看（主观，无验收标准）

✅ **正确示例**:
- `REQ-005: The system shall respond to user input within 200ms (95th percentile)`
  - 验收标准: 压测工具测得 P95 < 200ms
  - 测试方法: 性能测试

### 5. 写设计书

写入 `docs/harnessflow/01_DESIGN.md`。把已澄清的需求映射到：

- 模块划分与职责边界
- 对外契约与内部接口，含错误语义
- 状态变化与数据流
- 关键不变量（后续实现不允许破坏的东西）
- 现有代码证据：引用真实文件路径与行号，不凭印象
- 迁移与回滚条件
- 安全边界：认证授权、输入校验、密钥处理、网络暴露面
- 验证策略：怎么证明设计成立
- 重要取舍：选了什么、放弃了什么、为什么
- 原型与交互契约：当使用了截图标注、线框图或可点击原型时必须记录；没有交互原型时
  明确写 `None`。契约必须独立于原型本身可读，包含：
  - 原型路径或来源，以及版本/日期；用户提供但未复制进附件目录的截图和 Figma 也记录来源
  - 每个关键页面的状态（正常、加载、空数据、错误）
  - 每个关键操作的前置条件、反馈、成功结果与失败结果
  - 原型元素对应的需求编号（`REQ-NNN`）
  - 哪些行为是必须实现的规则，哪些只是视觉示意
  - 用户确认结果、未接受的建议和遗留分歧；未解决分歧阻断设计批准

每条需求编号必须能追溯到至少一个设计组件，在设计书末尾给出追溯表。
文件头 `Status:` 初始为 `Draft`。

### 6. 自检并交回

产出后逐条自检并把结果报给用户：

- 每条需求都能追溯到设计组件
- 外部契约、内部接口、错误语义无关键空白
- 迁移、兼容、回滚条件明确
- 验证策略足以证明设计成立
- 交互契约覆盖所有已确认的关键交互；对应的 REQ-ID 可追溯到原型或标注来源
- 安全边界已识别；如果新增了网络暴露的端点或接口而没有认证授权，明确指出这一点
不写产品代码，不改 `03_TASKS.json`，不改 `04_STATE.md`。设计附件只能写入
`docs/harnessflow/prototypes/`；其他目录的截图、Figma 导出或 HTML 只作只读输入。

然后告诉用户：交互契约无未解决分歧后，把两份文档的 `Status` 改为 `Approved` 再运行
/`hf-plan`。
不要自己把 `Status` 改成 `Approved`——批准是人的动作。

## 边界

- 不写产品代码，不改 `03_TASKS.json`，不改 `04_STATE.md`。
- 不臆造需求。用户没说、代码里也查不到的，列进未决问题，不要默默假设。
- 用户明确拒绝某个建议后，按用户的决定继续，不反复劝说。
